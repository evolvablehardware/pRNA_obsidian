- I think I'm going to simplify the eventsender/eventserver protocol before making the large promise-like system overhaul. I have a suspicion that this might not happen for a while. I think that all of the the stability issues from before were from the socket communication overhead with raw json. Now that this is fixed, the current system should continue to run fine at scale and reinforcing it is not as much of a priority.
	- Want:
		- Include event dataclasses in worker/control modules 
		- Register EventHandler functions with event dataclasses, they get passed in rather than json keys 
		- Convert socket messages to event objects
	- This should make it a lot easier for others to work with the system, as the current implementation relies knowing the actual json keys that are used with each event.
- Routing stuff
	- I think one of the biggest things is going to be making a better testing pipeline. I want to have tools to be able to probe specific nets to test outputs. Already partially have this with the routing tools, but will need to be able to configure input tiles in addition to output. Also need a firmware to test input/output combinations.
	- Also need to explore global nets more. I don't remember exactly but I got stuck working with them before I started using spans. I think I was trying to push values to them from logic tiles, which I now know that isn't possible.
	- Aside from these things I think we have most of the requirements to start on the graph-like representation. The largest thing to explore is what out/local/in combinations can be made.
		- I'm not sure actually how different a graph representation might be to what I already have going on in the routing repo with the addition of spans being disabled. It's already directly selecting inputs, output pairs with the caveat that it needs to evolve the /out -> local /in connections rather than a direct /out -> /in.
		- Currently, I see two ways to go about this. We could use a representation that is more rigid, but is a direct and deterministic transformation to the circuit representation. One way of doing this would be to hard code all of the local -> input connections. This would partially restrict what connections could be made however. The other approach would be to have something that transforms a more abstract representation into something concrete. Before considering the implementation of this, I think the largest thing to consider is how we would effectively design the representation to evolve on. Unless we don't look at the representation on a block-by-block basis, there will be mutually exclusive connections. However, what these are would likely be a function of what connections have already been made. 
		- It's worth noting that we could control the *direction* of the inputs. If we want to do approximate computing stuff, we don't want backtracking gates. We can simply enforce this by only allowing connections from neighbors on one side. This might open up enough local networks where each combination of inputs is possible
