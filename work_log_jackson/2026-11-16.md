## Log
- Planning on using similar system for client -> worker communications
- Rather than declaring json params for device state registration, declare a dataclass. Same system where it gets serialized on client transmission and then turned back into the corresponding dataclass upon being received. 
- I'd like a better registration format at some point, but I'm not yet sure the direction to go. Using register_args is kind of nasty, but I'm not sure if I want to use something like @dataclass yet.
	- The serialize/deserialize operations are not pure functions; for packets that include bitstream transmissions, the desired functionality is that the instance stores a file path, includes raw bytes in toJson, then writes the bytes and stores file name when reconstructed. In this case, the instance should be constructed from bytes and own the file, which does not fit the traditional dataclass decoration pattern. For now, going to stick to register_args until I figure out a way to account for this type of usage. 
	- Planning on just using the same BaseEvent registry. 
	- Not sure yet what I want to do afterwards. I think eventually sending event commands with the client should directly produce a response, but this is complicated by sometimes wanting to send multiple events at once and handling their results as they become available like BatchClient currently does.
		- Currently, I think I would implement a single event command as an option for blocking/non blocking callback, while multiple events would stream to a (event, result) generator
		- Second to allowing the server to send back error messages to specific requests, my hope is that the new system would untangle some of the mess in BatchClient. A good system should include enough functionality where ResultTracker becomes obsolete, along with the BatchClient specific event handlers that are used to pipe events to BatchFactory
		- Client call to send event adds event id to lookup table. Server sends event back with some metadata as the event id, I think may be best implemented outside of the normal data associated with an event aside event_id. Perhaps just a reply=BaseEvent additional parameter which defaults to none (should also have option to keep channel open for status updates). Client receives response and routes it to a different handler if it contains the new reply field (not yet sure if this should also propagate to normal eventhandlers). Looks up the handler for the message being replied to, which either directly returns the value, performs a callback, or yields (message, response).
- I'd also like to eventually move to dataclasses for registering reservables, but this is a bit unrelated since those are done with plain http instead of sockets.

	- Modify BaseEvent to be subclassable for other things. Add an option to ignore the init subclass hook on creation, then direct subclasses maintain their own registry with their own to/fromjson methods. Second subclasses go through init subclass hook as normal. Need to remember to overwrite cls attr or they will all go through same base class
	- Replace current AbstractState.register calls to those using structured events. Modify AbstractState.register take and pass structured events rather than args. Change worker/app to deserialize raw json into event dataclasses before passing into devicemanager. Change BaseClient.requestWorker to use structured events and update any method usage to new format.
	- Add reply metadata to server sent events

		- Need to keep this table clean from failed messages. I'm going to assume here for now that the worker can accurately detect when some sort of failure happens and can send a message afterwards. If not, the control should be detecting this failure. Right now sometimes a specific device fails without the worker noticing, but this is a worker issue and not something the client should be in charge of.
		- Callback will be directly performed on socket thread, direct return/generator uses cvs to pass data. For the case of multiple events, each reply id will just map to the same cv and return value queue.
